## 4. Формулировки SLI, SLO, SLA и математические формулы

### 4.1. Метрика 1: Успешность регистрации пользователей (Бизнес-индикатор)
* **SLI 1 (Service Level Indicator):** Доля успешных операций регистрации от общего числа попыток создания учетной записи за скользящее окно 5 минут:
  $$\text{SLI}_1 = \frac{\sum \text{rate}(user\_registration\_total\{status="success"\}[5m])}{\sum \text{rate}(user\_registration\_total[5m])} \times 100\%$$
* **SLO 1 (Service Level Objective):** Доля успешных регистраций должна быть не ниже **95%**:
  $$\text{SLO}_1: \text{SLI}_1 \ge 95\%$$
* **SLA 1 (Соглашение за скользящее окно 1 час / TBSLO):**
  Сервис регистрации считается доступным, если в течение **99%** времени в рамках отчетного окна целевой показатель $\text{SLI}_1 \ge 95\%$ выполняется:
  ```promql
  (count_over_time((sum(rate(user_registration_total{status="success"}[5m])) / sum(rate(user_registration_total[5m])) >= 0.95)[1h:])
    / count_over_time(sum(rate(user_registration_total[5m]))[1h:])) * 100
  ```

---

### 4.2. Метрика 2: Доступность бизнес-эндпоинтов API (RED Rate / Errors)
* **SLI 2 (Service Level Indicator):** Доля HTTP-запросов к бизнес-методам (`/api/projects`, `/api/tasks`), завершившихся без внутренних ошибок сервера ($5xx$):
  $$\text{SLI}_2 = \frac{\sum \text{rate}(http\_server\_requests\_seconds\_count\{uri=\sim"/api/.*", status!\sim"5.."\} [2m])}{\sum \text{rate}(http\_server\_requests\_seconds\_count\{uri=\sim"/api/.*"\} [2m])} \times 100\%$$
* **SLO 2 (Service Level Objective):** Доступность API должна составлять не менее **99.0%** (не более 1% ошибок $5xx$):
  $$\text{SLO}_2: \text{SLI}_2 \ge 99.0\%$$
* **SLA 2 (Соглашение за скользящее окно 1 час / TBSLO):**
  Доля минут, в течение которых доступность API держалась выше 99%, должна составлять не менее **99.5%**:
  ```promql
  (count_over_time((clamp_max(sum(rate(http_server_requests_seconds_count{uri=~"/api/.*", status!~"5.."}[2m])) / sum(rate(http_server_requests_seconds_count{uri=~"/api/.*"}[2m])), 1) >= 0.99)[1h:])
    / count_over_time(sum(rate(http_server_requests_seconds_count{uri=~"/api/.*"}[2m]))[1h:])) * 100
  ```

---

### 4.3. Метрика 3: Задержка ответа бизнес-эндпоинтов API (RED Duration / Latency)
* **SLI 3 (Service Level Indicator):** 95-й персентиль ($p95$) длительности обработки HTTP-запросов к бизнес-эндпоинтам за скользящее окно 2 минуты:
  $$\text{SLI}_3 = \text{histogram\_quantile}\left(0.95, \sum \text{rate}(http\_server\_requests\_seconds\_bucket\{uri=\sim"/api/.*"\}[2m]) \text{ by } (le)\right) \times 1000 \quad (\text{мс})$$
* **SLO 3 (Service Level Objective):** 95% запросов должны обрабатываться быстрее **500 мс** ($0.5$ с):
  $$\text{SLO}_3: \text{SLI}_3 \le 500\text{ мс}$$
* **SLA 3 (Соглашение за скользящее окно 1 час / TBSLO):**
  Доля времени, в течение которого $p95$ задержки не превышает 500 мс, должна составлять не менее **98.0%**:
  ```promql
  (count_over_time((histogram_quantile(0.95, sum(rate(http_server_requests_seconds_bucket{uri=~"/api/.*"}[2m])) by (le)) * 1000 <= 500)[1h:])
    / count_over_time(sum(rate(http_server_requests_seconds_count{uri=~"/api/.*"}[2m]))[1h:])) * 100
  ```

---

### 4.4. Метрика 4: Активность фоновой обработки напоминаний (Бизнес-индикатор)
* **SLI 4 (Service Level Indicator):** Интенсивность выполнения периодических задач планировщика `ReminderWorker`:
  $$\text{SLI}_4 = \text{rate}(reminders\_processed\_total[5m])$$
* **SLO 4 (Service Level Objective):** При наличии активных задач воркер должен регулярно фиксировать обработанные напоминания:
  $$\text{SLO}_4: \text{SLI}_4 > 0\text{ оп/сек}$$
* **SLA 4 (Соглашение за скользящее окно 1 час / TBSLO):**
  ```promql
  (count_over_time((rate(reminders_processed_total[5m]) > 0)[1h:])
    / count_over_time(rate(reminders_processed_total[5m])[1h:])) * 100
  ```

---

### 4.5. Комбинированный SLA приложения (Combined / Composite SLA)
В соответствии с лекцией и семинаром, комплексное здоровье системы оценивается по конъюнкции всех критических SLI. Если хотя бы один индикатор выходит за пределы SLO, данный интервал времени считается деградацией:

$$\text{Healthy}(t) = \big(\text{SLI}_1(t) \ge 0.95\big) \land \big(\text{SLI}_2(t) \ge 0.99\big) \land \big(\text{SLI}_3(t) \le 500\text{ мс}\big)$$

Формула расчета Combined SLA в **MetricsQL / PromQL**:
```promql
(count_over_time((
  (clamp_max(sum(rate(http_server_requests_seconds_count{uri=~"/api/.*", status!~"5.."}[2m])) / sum(rate(http_server_requests_seconds_count{uri=~"/api/.*"}[2m])), 1) >= 0.99)
  and
  (histogram_quantile(0.95, sum(rate(http_server_requests_seconds_bucket{uri=~"/api/.*"}[2m])) by (le)) * 1000 <= 500)
)[1h:]) / count_over_time(sum(rate(http_server_requests_seconds_count{uri=~"/api/.*"}[2m]))[1h:])) * 100
```

## 5. Реализация синтетического клиента (Пробера)

Пробер написан на Python 3 (`requests`, `logging`, `time`) и моделирует законченный пользовательский сеанс:
1. **Получение CSRF-токена:** Выполняет `GET /api/auth/csrf`, извлекает значение токена безопасности и подставляет заголовок `X-CSRF-TOKEN` во все мутирующие POST-запросы.
2. **Регистрация пользователя:** Генерирует случайное имя пользователя вида `prober_<random_hash>` и отправляет `POST /api/auth/register`. Наполняет метрику `user_registration_total`.
3. **Создание учебного проекта:** Отправляет `POST /api/projects` в рамках установленной HTTP-сессии (Cookie `SESSION`). Наполняет метрику `projects_total`.
4. **Создание учебной задачи с напоминанием:** Отправляет `POST /api/projects/{projectId}/tasks` со случайным приоритетом (`LOW`, `MEDIUM`, `HIGH`) и временем напоминания в прошлом (`remindAt: now - 10s`). Это наполняет счетчик `tasks_total` и провоцирует фоновый планировщик `ReminderWorker` на обработку напоминания, увеличивая `reminders_processed_total`.
5. **Чтение задач проекта:** Выполняет `GET /api/projects/{projectId}/tasks`, подтверждая доступность и консистентность чтения данных.
6. **Замер латентности и логов:** Пробер логирует каждую операцию с точным временем отклика в секундах и кодом ответа:
   ```text
   2026-10-30 20:05:06 [INFO] status=200  endpoint=GET /api/auth/csrf       duration=0.012s
   2026-10-30 20:05:06 [INFO] status=201  endpoint=POST /api/auth/register  duration=0.025s
   2026-10-30 20:05:06 [INFO] status=201  endpoint=POST /api/projects       duration=0.015s
   2026-10-30 20:05:06 [INFO] status=201  endpoint=POST /api/projects/1/tasks duration=0.022s
   2026-10-30 20:05:06 [INFO] status=200  endpoint=GET /api/projects/1/tasks duration=0.018s
   ```

### 5.2. Конфигурация через переменные окружения
* `PROBER_TARGET_URL`: базовый URL приложения (по умолчанию `http://localhost:8080`, в Minikube — `http://192.168.49.2:30000`).
* `PROBER_INTERVAL`: интервал между итерациями в секундах (по умолчанию `30`, для интенсивного теста и скринкаста настраивается на `2-3` секунды).

## 6. Модуль Chaos

#### 1. Модуль Chaos Engineering в бэкенде (`ru.uchebnyradar.chaos`)
Для демонстрации изменения поведения приложения на скринкасте реализован динамический тумблер сбоев:
* [`ChaosService.java`](file:///home/sec/SRE/scheduler_sre/backend/src/main/java/ru/uchebnyradar/chaos/ChaosService.java):
  * Хранит потокобезопасное состояние сбоя в `AtomicBoolean enabled`.
  * Определяет параметры сбоя: доля ошибок `failureRate = 0.2` (20%) и инжектируемая задержка `latencyMs = 1500` мс.
* [`ChaosController.java`](file:///home/sec/SRE/scheduler_sre/backend/src/main/java/ru/uchebnyradar/chaos/ChaosController.java):
  * REST API управления сбоем:
    * `GET /api/chaos/status` — возвращает текущее состояние (`true` / `false`).
    * `POST /api/chaos/enable` — включает симуляцию деградации.
    * `POST /api/chaos/disable` — отключает симуляцию и возвращает систему в нормальное состояние.
* [`ChaosFilter.java`](file:///home/sec/SRE/scheduler_sre/backend/src/main/java/ru/uchebnyradar/chaos/ChaosFilter.java):
  * Сервлетный фильтр с приоритетом `@Order(Ordered.HIGHEST_PRECEDENCE + 1)`.
  * **Защита контура управления:** Пропускает без сбоев запросы к `/api/chaos/**`, `/actuator/**` и `/api/auth/csrf`.
  * **Инъекция сбоев:** При активном тумблере перехватывает запросы `/api/**`:
    * С вероятностью 20% возвращает HTTP 500 Internal Server Error с телом `{"status":500,"error":"Chaos Error"}`.
    * С вероятностью 40% вызывает `Thread.sleep(1500)`, моделируя сетевую/базовую деградацию.
